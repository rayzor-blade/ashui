# ashui in a page

Run ashui programs in a browser by compiling their bytecode to WebAssembly
with [Ash](https://ash.rayzor.tech). The target is `wasm32-wasip1-threads`.
The page's canvas acts as the window. hlwindow's `xwindow.wasm` handles input,
size and scale; hlwgpu's `xgpu.wasm` renders through WebGPU.
`blinc_abi` supplies a third native module.

## What you need

- ashui, hlwgpu and hlwindow from Haxelib. Each release ZIP carries its web build
  under `web/`, so nothing is compiled from Rust.
- `ash-future` from Haxelib, and Ash, with threads in a page working (a release
  after 0.1.10).
- To look at it, a browser with WebGPU, and a server that sends the two headers a
  threaded module needs. `ash serve` does.

## Build it

An app's hxml is the desktop one with two more defines:

```hxml
-cp src
-lib ashui
-lib ash-future
-D wasm
-D ashui_window
-main App
-hl dist/app.hl
```

```sh
haxe web.hxml
ASH_WASM_FIBERS=1 ash --build dist/app.wasm --target wasm32-wasip1-threads dist/app.hl
ash serve dist
```

Fibers let `await` suspend the program while the browser completes a GPU
promise, including during window creation. The Haxe build stages the web
libraries beside the bytecode. `ash --build` adds the browser host files:

| File | From |
| --- | --- |
| `index.html`, `ashui-host.mjs` | ashui: the page, and the script that runs it |
| `blinc_abi.wasm` | ashui |
| `xgpu.wasm`, `gpu.mjs`, `gpu-worker.mjs`, `gpu-agent.mjs`, `hlwgpu.js` | hlwgpu |
| `xwindow.wasm`, `xwindow.mjs`, `xwindow_wire.mjs` | hlwindow |
| `app.wasm`, `worker.js`, `thread.js`, `display.js`, `ash_browser.js`, `ash_browser_bg.wasm` | `ash --build` |

The output module uses the bytecode name: `app.hl` becomes `app.wasm`.

## The page

The canvas fills the page. Layout follows its size and scale when the browser
resizes or moves between screens. The program's requested window dimensions
do not override the canvas size.

A loading message remains until the first GPU frame. The page reports missing
cross-origin isolation, unavailable WebGPU and program termination.

Program output goes to the browser console. Add `?log` to display it on the
page as well. `?arg=value` passes a command-line argument to the program.

A custom `index.html` beside the output is preserved. ashui only replaces its
own page or the page generated by `ash --build`. Define `ashui_no_page` to
skip staging both `index.html` and `ashui-host.mjs`. For a custom host,
use `ashui-host.mjs` as the startup reference.

## What a page does not have

Browser builds do not have a runtime filesystem. Supply environment variables
through URL parameters such as `?env=NAME=value`.
`Css.loadFile`, `Bitmap.load`, `Fonts.load`, `Gltf.load` and similar APIs use
`ashui.core.Assets`, which resolves filesystem paths or embedded assets.
Embed a directory at compile time:

```hxml
--macro ashui.core.Assets.embed("assets", "assets")
```

Files under `assets` become available as `assets/<path>`.
`Bitmap.load("assets/photo.png")` then works on desktop and web.
The second argument sets the runtime path prefix. This can differ from the
build path, for example `("../tools/snapshot/assets/map", "../assets/map")`.
`Bitmap.embed`, `Fonts.embed` and `CompiledCss` already embed their inputs
at compile time and do not need directory registration.

Precompress model textures with `tools/bcpack` and ship their `.dds` sidecars.
Runtime block compression is too costly for the browser: it can take seconds
and require memory comparable to the source image. The page uploads prepared
files directly. See ashui-canvaskit's README.

The program uses one shared WebAssembly memory. It grows as needed and does
not shrink. The memory ceiling is 1 GiB. Set `?env=ASH_GC_HEAP_MB=400` to
limit the heap to 400 MB.

It has no system fonts either; the next section says what a build carries. The
debugging tools that write files, such as `MotionRecorder`, are not for a page.

## When a page stops

Add `?debug` or `?watch` to log browser animation-frame statistics once per
second. `?log` also displays the output over the app:

```
[page] 60 animation frames in 1002 ms, longest gap 17 ms, 4 ms since the last, program memory 606 MB
```

The window and audio loops use browser animation frames. The window loop
forwards redraw requests; the audio loop tracks playback position.
Use the statistics to distinguish these cases:

- The page is frozen but the frame count advances: the program is stuck or waiting.
- The count is 0 and `page hidden` is reported: the browser is not displaying it.
- A long gap appears: the browser thread was busy.

Add `?env=ASHUI_FRAME_STATS=1` for program-side frame counts and redraw timeouts.
A redraw timeout means the program waited a second without a browser redraw.
Add `?env=ASH_GC_STATS=1` to log collections. Repeated `origin=large-exhaustion`
with `freed=0` indicates an exhausted heap.

## Media

Web audio uses hlavi's web build. Add `-lib hlavi`, `-D wasm` and its
`NativeInstall` macro to stage `xavi.wasm` and the supporting scripts.
Media files load by URL, so copy them beside the page during compilation:

```hxml
--macro ashui.macro.WebPage.copy("assets/audio", "audio")
```

Open the served path, for example `MediaPlayer.open("audio/track.m4a")`.
Format support follows the browser, usually MP3, AAC in M4A, Ogg and WAV.

Browsers require user input before starting sound. A blocked play request
is retried on the next pointer press or key event. Starting playback from
a button normally satisfies this requirement immediately.

Web support currently covers audio playback. Video frames, equalization,
codecs, queues and muxers are unavailable on the web.

## Fonts

Wasm builds include Arimo, with Helvetica/Arial-compatible glyph widths.
It supplies unspecified fonts, `system-ui` and `sans-serif`. Embedded faces
named Helvetica, Helvetica Neue or Arial take precedence. Register them
with `Fonts.embed` before laying out text.
Define `ashui_no_default_fonts` to omit Arimo. See `ashui.text.Fonts`.

## Threads

Background work runs on Workers created before program startup.
GPU commands are submitted as a batch per frame, avoiding worker wakeups
and device queries during drawing.

## Try it

`tests/wasm/run.sh` builds a demo for a page, serves it and opens it in your
browser, and runs no tests:

```sh
tests/wasm/run.sh            # the README's banner: a glTF car, glass panels, gauges, a street map
tests/wasm/run.sh Dashboard  # apps/dashboard: the same dashboard as an app, with working pages and music
tests/wasm/run.sh WindowPage
```

The runner builds `blinc_abi`, hlwindow and hlwgpu from sibling checkouts
on first use, then caches them in `tests/bin/web`. `--rebuild` refreshes
the libraries. `--port` selects the server port; `--no-open` skips browser
launch. On macOS, `BROWSER="Google Chrome"` selects a browser.
Use `ASH=` to select the Ash executable.

`tests/wasm/smoke.sh` builds the libraries and runs these checks in headless Chrome:

- A small web-runtime check.
- The framework smoke suite.
- Pixel checks on a window canvas.
- The banner, which must still be drawing after 25 seconds.
- The dashboard's pages, music and light/dark appearance.

`tests/wasm/smoke.sh Banner` runs only the banner check.
The runner also requires Node 22+, Google Chrome and ImageMagick.
Set `CHROME=` to select a Chrome executable.

### Building native dependencies from source

Repository runners need sibling library checkouts and a Rust nightly with
`rust-src` for the first native build. Package users receive these binaries
through Haxelib.

Each library's `scripts/build_wasm.sh` builds its web files.
Use `-D hlwgpu_web=<directory>` and `-D hlwindow_web=<directory>` to select
custom output directories. Set `RUST_NIGHTLY=nightly-2026-08-25` or an older
supported nightly. Rust 1.101 nightlies import `pthread_key_*`, which Ash
does not yet provide; the scripts reject those builds.

## How big it is

The example window built by `tests/wasm/smoke.sh` loads about 25 MB:
15 MB for the program, 7 MB for `blinc_abi`, 1.8 MB for Ash's browser host,
and under 1 MB for the GPU and window modules. Transfer size falls to
4.9 MB with Brotli or 6.5 MB with gzip. Check that your host compresses wasm.

Most of the program is compiled Haxe. It also includes 2.5 MB of Ash runtime
and a 4.7 MB data section, roughly half of which is compressible zero padding.

The dashboard program is 23.0 MB, or 5.5 MB with Brotli. Its sections are:

- 13.2 MB of code: 9.9 MB compiled from Haxe and 2.4 MB of Ash runtime.
  The Haxe portion has 5,921 wasm functions from 3,095 Haxe functions.
- 8.3 MB of data: about 3.5 MB of embedded car, texture, map and font assets;
  the remainder is bytecode.

The default build applies dead-code elimination to the standard library.
`-dce full` also removes unused application code. In this test it reduced
the program to 20.4 MB, or 5.1 MB with Brotli, while passing the page test.
Set `ASHUI_HAXE_FLAGS="-dce full"` to pass it through `tests/wasm` or
`tests/run.sh`. Check reflection-dependent code before enabling it.

Compression had the larger effect on loading time: at 20 Mbit/s, readiness
improved from 19 s uncompressed to 10 s with Brotli.

Ash's host fetches the program and libraries concurrently, then prepares each
on an idle agent as bytes arrive. In headless Chrome with network throttling,
Brotli and an empty cache, the dashboard reached `ashui: ready` in:

| Connection | Concurrent loading | Sequential loading |
| --- | --- | --- |
| 10 Mbit/s, 80 ms latency | 12.8 s | 14.5 s |
| 50 Mbit/s, 40 ms latency | 4.9 s | 6.1 s |

`ash serve` does not compress responses. The same page took 45 s at 10 Mbit/s
without compression. Measure production loading on a compressing host under
representative network conditions.

`ASHUI_WASM_SMALL=1 tests/wasm/smoke.sh` builds as a site would ship, and prints each
file's size:

- `blinc_abi` with fat LTO and `opt-level=z`: 6.9 MB becomes 5.5 MB;
- the programs with `ASH_LLVM_PASSES='default<Oz>'`: 15.2 MB becomes 14.6 MB;
- the name section, which only helps debugging, dropped from every module with
  `scripts/strip_wasm_names.py`: about 1.4 MB between them.

Together that is about 21 MB of files, 4.4 MB with brotli and 5.8 MB with gzip.
In these measurements, Binaryen's `wasm-opt` output compressed worse than
Ash's output. Version 132 also emitted import encodings unsupported by some browsers.
